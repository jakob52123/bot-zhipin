## 2026-11-22 加埋点

72. **全站埋点自建：前端 `theme/track.ts` 批量发到 `POST /api/events`，存进 D1 新表 `events`，用 `npm run report` 只读查询、打印中文报告**（用户 2026-11-22 定）。用户原话：「埋点的设计需要给我加上」。三个选择由用户定：数据存哪选了「自建：存进本站 D1」；怎么看选了「命令出中文报告」；隐私边界四项里只选了「记录搜索词原文」。设计正本是 `docs/dev/TRACKING.md`，事件表正本是 `functions/_lib/events.ts`。
    - **为什么要做**：开站到 11-22 只有 4 种按钮计数（导入、复制安装提示词、复制开场白、复制口令），而且都在复制之前上报。Prompt、Skills 的复制、搜索、筛选、浏览量、外链、投稿漏斗一概没记，判断不了三个模块好不好用、该收什么。
    - **北极星**是「拿走会话数」：会话里至少有一次导入或复制，就算一次拿走会话。拿走事件不论复制成没成功都算，因为退回手动复制时多半也复制走了。
    - **热度计数不变**（第 3、59 条）。`/api/click` 带去重，是页面上展示的功能；埋点是另一条原始数据流，不去重，只给维护者看。导入和三种复制照旧 `reportClick`，另外再记一条埋点。
    - **隐私**：
      - 不用 cookie、不用 localStorage 存身份、不跨天追踪、不加第三方脚本。
      - 会话号放 sessionStorage，关掉标签页就没了。
      - 当天访客号用 `hashIp` 带上日期算，第二天就对不上。
      - 搜索词存原文，截到 40 字；邮箱、7 位以上的数字打码。
    - **`events.name` 不加 CHECK**：加事件不用迁移，这是第 60 条重建表的教训。迁移 `0005` 只新建表。
    - **放弃的方案**：
      - Cloudflare Web Analytics（多一个第三方脚本，浏览量会重复）；
      - Umami、PostHog、百度统计（国内慢或打不开，或者数据交给别人）；
      - 网站里的管理后台（要登录鉴权，工作量翻倍）；
      - 定时发飞书（要一台常开的机器）；
      - 排除维护者自己的访问、尊重「请勿追踪」、页脚隐私说明（用户这次都没选）。
    - **已知代价**：
      - 维护者自己点的也会算进去，流量小的时候会明显拉高数字。
      - 组件已接上埋点。⌘K 搜索面板（#38）也已接上 `search`：选中或关闭时记一次，空词不记。
